## Design Specificity Verdict

**LLM assessment**: This does not read as authored specifically for a police-organized charity Hyrox event — it reads as a well-executed generic multi-step SaaS signup wizard (4-step: person A → person B → team → review, chip-style radios, sticky step rail, review-cards-with-edit-links) wearing the Tactical Briefing skin. Nothing in the structure, copy voice, or information hierarchy signals "police" or "charity" beyond the header wordmark and the (factually accurate, not designed-in) administration dropdown options. PRODUCT.md names the Orphéopolis charity angle as a positioning pillar meant to inform "messaging and CTA framing, not just 'sign up for a race'" — that framing is entirely absent from this registration flow itself; the form never mentions the charity, only a bare "60 €" fee. The visual skin is doing all the specificity work; the interaction design underneath is templated.

**Deterministic scan**: `detect.mjs --json` against `ui/src/app/pages/inscription/` and `ui/src/app/components/ui/inscription-form/` exits 0 with an empty findings array — clean on the static/regex pass. However, the live browser-injected overlay (full rendered-DOM pass) found 1 anti-pattern the static scan missed: `call-caps-body` on `p.chip-caption` — 38 characters of body text rendered `text-transform: uppercase`. This is a real, correctly-caught violation, not a false positive: `.chip-caption` (used for "Catégorie *" and "Participer en tenue d'intervention ? *") sets `text-transform: uppercase` and 0.78rem/0.14em tracking but never overrides `font-family`, so it inherits the `:host`-level `font-family: $font-body` (Cabin) — landing it squarely on DESIGN.md's own "Uppercase-Only Rule": *"Cabin never appears in all-caps for running text."* The fix is narrow: give `.chip-caption` the system's Label font token (Lemon Milk) instead of silently inheriting Cabin body font, matching how the rest of the system's uppercase eyebrow/label text is built. The discrepancy between the two detector passes (static: clean, live-rendered: 1 finding) is consistent with the tool's documented behavior — component-level SCSS cascade effects on rendered text only surface once the page actually renders — and is worth noting for future runs on this target, not a tool malfunction.

**Visual overlays**: Browser mutation/injection succeeded in Assessment B's isolated tab (not the user's own browser in this run, since both assessments ran in sub-agent-controlled tabs that were closed after evidence collection) — no persistent user-visible overlay remains open. The console output was: `[impeccable] 1 anti-pattern found` → `call-caps-body — text-transform: uppercase on 38 chars of body text — element: p.chip-caption`.

## Overall Impression

The component-level execution is genuinely clean and faithful to the Tactical Briefing tokens — fields, chips, buttons, and the step-4 review cards all read as on-system. But three things undercut it: a confirmed **logic bug** that strips user control at the highest-stakes moment in the flow (can't cancel the auto-redirect to an external payment site), a **shipped fix that doesn't actually work** in the live app (scroll-to-first-invalid, independently reproduced twice), and a **systemic over-use of the system's own scarcest resource** (hazard yellow appears 8+ times simultaneously by step 3, against DESIGN.md's own explicit rule). The single biggest opportunity: stop treating "Confirmer et payer" as an instant, timed hand-off — make the post-submit confirmation screen a calm, user-paced stop with an explicit "Continuer vers Yurplan" action, which would simultaneously fix the P0 control-loss bug and better serve the peak-end moment of a flow whose one real strength (the Yurplan warning copy) is already trying to be reassuring.

## What's Working

1. **The step-4 Yurplan warning box** (`.review-warning`) — naming the partner explicitly, promising the registration persists even if payment fails, and giving a named contact + phone number is exactly the right trust-repair pattern for an off-site payment redirect to a police-adjacent, trust-sensitive audience. Clearly the product of the prior fix pass paying off.
2. **URL-driven step state** (`?step=N`, `queryParamsHandling: 'merge'`) — makes the wizard properly deep-linkable with working browser back/forward, which most hand-rolled multi-step forms get wrong. (Trade-off: this same mechanism is also what lets a first-time visitor land on an empty, data-less step 4 — see Priority Issues.)
3. **Correctly-wired `aria-invalid`/`aria-describedby` on every text input**, confirmed live: each invalid field gets its own red border and an inline "Ce champ est requis." (or a specific message for email/category/etc.) directly below it, with the right ARIA plumbing for a screen-reader user tabbing field-by-field — even though the higher-level focus/scroll/live-region behavior around it is broken (see P1 below).

## Priority Issues

**[P0] Auto-redirect to Yurplan cannot be cancelled once submitted**
- **Why it matters**: `submit()`'s success handler unconditionally schedules `setTimeout(() => { window.location.href = this.url; }, 2000)`, while `closeModal()` only sets `showModal = false` and never clears that timeout. A user who clicks "Fermer" on the confirmation modal — to re-read the phone number, or reflexively — is still forcibly redirected off-domain 2 seconds later regardless. This is the highest-stakes moment in the entire flow (a police officer being sent to pay 60€ on a third-party site) and the user has no way to stay on the page. Directly undermines PRODUCT.md's "payment and account state must never be ambiguous" principle and Nielsen's User Control heuristic.
- **Fix**: Store the `setTimeout` handle and `clearTimeout()` it inside `closeModal()`; better still, drop the automatic redirect entirely and make an explicit, un-timed "Continuer vers Yurplan →" button the only path off the confirmation screen.
- **Suggested command**: `/impeccable harden`

**[P1] The prior fix pass's scroll-to-first-invalid does not work live**
- **Why it matters**: `scrollToFirstInvalid()` was added specifically to fix this in the last pass, and both assessments independently reproduced its failure: after clicking "Continuer" on an invalid step, `document.activeElement` stays on the Continuer button and `window.scrollY` is unchanged, even though the target selector correctly resolves to the first invalid field and a manually-invoked `scrollIntoView()` on that same node does move the page. Combined with no `aria-live` on the step-error summary and no `aria-describedby` on the chip-group radiogroups, a user whose invalid field is below the fold (increasingly likely on step 2/3) — or any keyboard/screen-reader user — gets no signal that "Continuer" did anything at all.
- **Fix**: Debug why the code path doesn't fire on a real click (worth checking Angular zone-patched `setTimeout` timing vs. the button's native focus retention after a click); add `aria-live="polite"` to `.step-error`; wire `aria-describedby` from each chip-group's error paragraph back to the `role="radiogroup"` container.
- **Suggested command**: `/impeccable harden`

**[P1] "One Signal Rule" is violated throughout the form, not just on the landing page**
- **Why it matters**: Verified live — by step 3 filled, the screen simultaneously shows the yellow brand mark, the yellow hero word, three cumulatively-lit yellow step numbers, a yellow progress-bar segment, a yellow active chip, a yellow checked checkbox, and the yellow primary CTA. DESIGN.md is explicit: "ration Hazard Yellow: one dominant yellow element per screen" and warns that over-use "reads as alarm fatigue, not urgency, the moment it stops being rare." The step-rail's cumulative "lit" treatment (applies to every completed step, not just the current one) is the single biggest driver — it guarantees an ever-growing count of yellow numerals as the user progresses through exactly the screen meant to feel calm and trustworthy at the highest-friction (payment) moment.
- **Fix**: Reserve yellow for the current step number only; give past/completed steps a neutral treatment (checkmark or white numeral). Consider a secondary "selected" treatment (white fill + yellow border, rather than full yellow fill) for chips/checkboxes so multiple simultaneously-active selections don't all compete at full saturation.
- **Suggested command**: `/impeccable quieter`

**[P1] No guard or empty-state when a step is opened with no prior data**
- **Why it matters**: Verified live — navigating directly to `/inscription?step=4` (or clicking "04 Récapitulatif" in the step rail) on a fresh session renders the review screen with every `dt`/`dd` pair showing a label and no value, no placeholder, no "non renseigné" — nothing to distinguish an expected empty state from a broken page. The submit button is correctly `disabled` so there's no data-integrity risk, but the visual impression is bad for a first-time visitor who explores the step rail out of curiosity, and this is plausibly a less-forgiving audience (police officers evaluating an institutional-adjacent tool) for a glitchy-looking first impression.
- **Fix**: Disable/gray out step-rail buttons beyond the furthest step the user has actually validated, or render an explicit empty-state message ("Complète d'abord les étapes précédentes") when a review section has no data.
- **Suggested command**: `/impeccable harden`

**[P2] Small copy and typography consistency slips**
- **Why it matters**: Two independent, narrow but real inconsistencies. First, `step3.administration`'s required-message reads "Merci de sélectionner **ton** administration" — the only informal-*tu* string on the page; every other message and the step-4 warning paragraph use formal *vous*, a jarring register break for a professional audience. Second, the detector's one live-rendered finding: `.chip-caption` (the "Catégorie *" / "Participer en tenue d'intervention ?" labels) renders 38 characters of Cabin body text in `text-transform: uppercase` because it never overrides the inherited `:host` `font-family: $font-body` — a direct, correctly-flagged violation of DESIGN.md's "Uppercase-Only Rule" ("Cabin never appears in all-caps for running text").
- **Fix**: Change "ton" → "votre" in the `requiredMessages` map (`inscription-form.component.ts`); give `.chip-caption` the system's Label font token (Lemon Milk) instead of inheriting Cabin.
- **Suggested command**: `/impeccable polish`

## Persona Red Flags

**Jordan (Confused First-Timer)** — the literal target of this multi-step signup:
- Clicks "04 Récapitulatif" in the step rail out of curiosity (a common exploratory move in a step-rail UI) and lands on a wall of blank labels with no explanation — reads as the site being broken before Jordan has filled in a single field.
- Submits step 1 empty (plausible — the required asterisks are small and color-only): gets correctly red-bordered fields and inline error text, but nothing scrolls or focuses to draw the eye, so if the invalid field is below the fold, "Continuer" appears to silently do nothing.
- After a successful submission, starts reading the modal's genuinely reassuring Yurplan/phone-number message — then is yanked off-site mid-read by the 2-second auto-redirect with no way to pause. For someone already nervous about being told "you're about to pay 60€ on a different website," this is precisely the wrong moment to lose control.

**Sam (Accessibility-Dependent User)** — screen reader / keyboard-only:
- Hitting Enter or clicking Continuer with invalid fields produces zero assistive-technology feedback: focus stays on the button, the error summary has no `aria-live`, so nothing is announced. Sam must manually tab through every field to discover which ones are flagged.
- The chip-group `role="radiogroup"` controls and their error paragraphs have no `aria-describedby` link at all (unlike the correctly-wired text inputs) — a screen-reader user focused on the category/outfit/version radios gets no programmatic association to "Merci de choisir une catégorie."
- The required step-3 consent checkbox is buried mid-sentence inside a full paragraph of legal-ish text (the only differentiator from the visually-identical, optional volunteer checkbox is a small embedded asterisk) — easy for a user navigating by landmark/heading rather than reading every paragraph to miss that it's mandatory until submission fails.

## Minor Observations

- Invalid-checkbox state has no visual treatment on the checkbox/row itself (only the message below turns red), inconsistent with how text inputs signal invalidity via border color.
- The optional volunteer checkbox and the required consent checkbox use visually identical `.checkbox-row` styling; the only differentiator is a small yellow asterisk mid-sentence.
- The sessionStorage draft auto-save (`FORM_STORAGE_KEY`) is a nice technical safety net but is completely silent — no "we restored your progress" affordance, no visible way to discard a stale draft (relevant on a shared/kiosk device, or if a participant's details change between visits).
- Step transitions do not scroll to top — confirmed live: clicking Continuer from a scrolled-down position on step 1 renders step 2 at the identical scroll offset, so the user doesn't see the "PARTICIPANT 2" heading or first fields without manually scrolling up.
- Live 375–390px mobile rendering could not be confirmed in this run — the browser tool's `resize_window` reported success but had no measurable effect on `window.innerWidth`/`outerWidth` across repeated attempts in both assessments' isolated tabs (an environment/tool limitation, not a page bug). Static SCSS inspection shows the previously-reported 9px review-grid overflow fix is structurally present (`.review-card__body` grid track changed to `minmax(110px, auto) minmax(0, 1fr)` with `overflow-wrap: break-word` added on `dd`, and both the step 1/2 field-grid and the outer `.layout__grid` use `auto-fit, minmax(280px, 1fr)`, which collapses to one column without a dedicated breakpoint) — plausible by inspection but genuinely unverified live, and this exact surface has a history of shipping mobile overflow bugs, so it should be spot-checked on a real device or working viewport emulation before being treated as closed.
- The outfit chip group's third option label ("Non.") visibly wraps to its own row on a full desktop viewport because the second option's label is 38 characters long — reads as an uneven 2+1 grouping rather than a clean 3-option set.

## Questions to Consider

- If the "One Signal Rule" is being violated this consistently across both the landing page and this core conversion form, is the rule itself impractical for a multi-state wizard (where "current step," "selected option," and "primary action" all plausibly want the same emphasis color), or does the component library need a genuine secondary-emphasis treatment so not every "selected/active/lit" state has to compete for the same single color?
- Payment happens entirely outside this app on Yurplan — why force an *automatic*, timed redirect at all, rather than landing on a calm confirmation screen with an explicit, un-timed "Continuer vers Yurplan →" the user clicks when ready? The current design seems to solve a friction problem this audience probably doesn't have, while creating a real loss-of-control problem at the highest-stakes moment in the flow.
- PRODUCT.md names Orphéopolis and the charity angle as a core positioning pillar meant to inform messaging and CTA framing beyond "sign up for a race" — should any of that appear inside the registration form itself, or is it meant to live on the landing page only?
